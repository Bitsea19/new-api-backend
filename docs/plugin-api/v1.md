# 任务插件 API v1

任务插件 v1 有两个独立的入口面。`meta.routes` 注册由插件自身拥有的原生 URL；`meta.protocols` 声明宿主拥有的协议，但不注册也不复制其 URL。`apiVersion` 保持为 `1`。

## 清单（Manifest）

```js
export const meta = {
  apiVersion: 1,
  key: "vendor",
  name: "Vendor",
  version: "1.0.0",
  author: {name: "Author"},
  description: {en: "Video generation via the vendor API", zh: "通过厂商接口生成视频"},
  models: ["vendor-model"],
  fetchMode: "per_task",
  routes: [
    {method: "POST", path: "/vendor/v1/jobs", type: "submit", decode: "createJob", render: "jobCreated"},
    {method: "GET", path: "/vendor/v1/jobs/:task_id", type: "query", render: "jobStatus"},
  ],
  protocols: [{name: "openai_responses", supports: ["stream", "sync", "background"]}, "openai_video"],
};
```

`submit` 与 `dynamic` 路由必须提供 `decode` 和 `render`。`query` 路由必须提供 `render`、禁止提供 `decode`，并使用 `taskIdParam`（默认 `task_id`）：取该名称的路径参数；若路径中没有该参数，则取同名的查询字符串参数，正如 MiniMax 的 `GET /v1/query/video_generation?task_id=` 所做的那样。这些名称只指向 `native` 的可调用成员。一个插件的路由（连同下文的 `/{key}` 地址）必须在方法或归一化后的路径形态上互不相同；路由索引与其插件版本一同原子发布。

插件声明其供应商自己的路径。网关会在该路径上提供每条路由，同时也在 `/{key}` 下再提供一次：doubao 的 `POST /api/v3/contents/generations/tasks` 同时也是 `POST /doubao/api/v3/contents/generations/tasks`，后者只会到达 doubao。首段即为插件 key（或其真前缀）的路由已经是插件自己的地址，不会再复制一份：alibaba 的 `/ali/...`、sunoapi 的 `/suno/...`、hailuo 的 `/hailuo/...`。内置插件的自有前缀受保护：其他插件不得占用它们作为自己的 key，其下的顶层路由也不会被提供。

多个插件可以声明相同的方法与路径形态，同一模型下也如此。每个声明了 `submit` 路径的插件都按 key 升序解析请求；第一个接受它的插件确定模型名，其他接受同一模型的插件留作候选，由选中的渠道决定哪个插件实际执行 —— 与共享宿主协议上的情形一样，该任务按该插件的 `<pluginKey>::<model>` 表达式计费。解码器的 `model` 按宿主协议的方式匹配：大小写变体代表所声明的模型，任务采用声明时的拼写；某个已启用渠道列出并通过 `model_mapping` 映射的别名仍是任务的模型，驱动从 `ctx.upstreamModel` 读取映射后的名称。单个候选的拒绝会原样返回给客户端；当多个候选全部拒绝时，客户端收到的每条消息都会前缀上给出它的插件 key。`query` 路径通过任务自己的插件作答，归属权由 key 升序中的第一个插件持有；没有任何插件归属的任务视为不存在。`dynamic` 路径通过第一个持有这些任务的插件回答查询，否则继续作为提交处理。每个插件按自己声明的名称读取路径参数，因此 `/v1/videos/:request_id` 与 `/v1/videos/:task_id` 可以共用同一路径。位于同一位置的 catch-all（`*name`）与另一个插件的字面量段无法共存；此时网关会以路由错误排除其中一个插件。

路由须避开保留命名空间 `/v1/tasks`、`/assets` 和控制台页面，且 key 不能是 `api` 或它们的首段，否则该插件编译失败。其他宿主命名空间是 `api` 以及每个宿主路由的首段（`v1`、`v1beta`、`mj`、`pg`、`dashboard`）。只有内置插件（`plugins/tasks/<key>`，即使被上传版本覆盖或被关闭）能在这些命名空间的顶层路径上被提供，且只能出现在没有同方法的宿主路由（或其引起的尾部斜杠重定向）先应答的位置。当顶层路由的首段是另一个插件的 key 或内置插件的自有前缀时，它同样不会被提供。这类路由仍会在 `/{key}` 下被提供，插件列表（`GET /api/plugin/task`）与详情页会在 `skipped_routes` 中列出它（`"POST /v1/videos/probe"`）。key 是宿主段或内置插件自有前缀的插件，会以路由错误被排除。`query` 路由的任务 id 参数只接收网关任务 id，因此不会与字面量宿主段冲突：`GET /v1/videos/text2video/:task_id` 可以与宿主的 `GET /v1/videos/:task_id/content` 并存。有两条宿主路由会优先把匹配请求交给插件路由，因此插件路由可以与它们重叠。`GET /v1/videos/:task_id` 在任务是通过该插件的某条原生路由提交（走供应商路径、`/{key}` 下或其自有前缀下）且插件提供匹配该请求的 `query` 路由时，由任务自己的插件作答；其他任务一律得到 OpenAI 视频对象。`POST /v1beta/models/{model}:predictLongRunning` 会先走到匹配的插件路由，然后才进入 Gemini 中转的鉴权、限流与渠道选择；其他 Gemini 动作，以及没有插件路由匹配的请求，仍由中转处理。

`routes[].retainResult` 是 `submit` 与 `dynamic` 路由上的可选布尔值，默认 `true`。只在每次成功提交都立即完成的路由上声明 `retainResult: false`，通常是供应商没有可再查询任务的同步图片 API。对这类结果，宿主不持久化 `task.data`，此后该任务在所有获取面上都视为不存在：插件自己的 `query` 路由、`GET /v1/responses/:response_id`、`GET /v1/videos/:task_id` 及其内容、产物列表与产物内容。任务行仍会保留用于计费与任务日志。提交呈现器仍会收到完整的内存态 `task.data`，且 `extractUsageOnComplete` 在持久化之前运行，因此结算不变。因为不持久化，这类路由的提交应答、每个 SSE 事件及其内存态 `task.data` 最多可达 `MAX_FILE_DOWNLOAD_MB`（默认 64 MB）而非 1 MiB，这让供应商可以用 Base64 图片作答；插件状态仍保持 1 MiB 限制。在声明该字段的路由上返回的异步结果会照常保留并可获取，同时记录一条警告。`query` 路由拒绝该字段。`openai_responses` 与 `openai_video` 始终保留结果，因为它们的交付物通过宿主产物 URL 提供；希望预览而存储更少的插件，应改为从 `parseSubmitResponse` 返回一份紧凑的 `taskData`。`openai_image` 在创建应答中直接内联图片，因此该协议上的立即终态结果与 `retainResult: false` 一样被丢弃，而由请求内轮询完成的结果保留轮询器写入的快照。这是 apiVersion 1 的增量扩展：旧宿主会拒绝这个未知字段。

`routes[].models` 可选地把 `submit` 或 `dynamic` 路由限制到 `meta.models` 的一个子集。宿主在任何 JS 钩子运行之前匹配顶层规范化的 `model` 请求体字段，列出模型的大小写变体或渠道别名都算作已列出；缺失、非字符串或未列出的模型会以 400 拒绝（插件路由是独占路径，没有中转回退）。只在模型位于请求体顶层时才声明它 —— 把模型嵌套在其他位置的供应商格式应省略 `models` 并在 `decode` 内部过滤。`query` 路由没有请求体，拒绝该字段。

每个 `protocols` 条目声明占用一个宿主协议。定义了模式的协议必须以对象形式声明，并显式给出 `supports`；裸字符串形式只对没有模式的协议有效（`openai_video`、`openai_image`）。`supports` 声明插件在 `openai_responses` 上接受哪些客户端请求形式：`"stream"`（`stream: true`）、`"sync"`（两个标志都不设，调用会阻塞到终态 Response）、`"background"`（`background: true`，创建立即返回待处理的 Response）。不支持的请求形式会在渠道选择阶段以 400 拒绝，早于任何插件钩子运行，也早于计费。获取（`GET /v1/responses/:response_id`）不是一种模式：每个已创建的 Response 始终可获取。

`{name, models}` 仍然把该协议的端点绑定收窄到 `meta.models` 的子集，并与 `supports` 组合。未列出的模型永远不会在该协议路径上进入插件 —— 它们会落到内置 Go 中转。多个插件可以在同一宿主协议路径上占用同一模型，包括 type-61 插件与带旧版 `channelTypes` 的插件。候选按插件 key 升序排列。选中的渠道决定实际执行的插件：旧渠道看渠道类型，type-61 渠道看 `setting.task_plugin_key`，type-60 New API 渠道看 `setting.task_plugin_key` / `setting.task_extend_plugin_keys` 的绑定项。type-60 渠道可以扩展任意数量的插件，因为上游网关可能托管许多插件；当多个已绑定插件共用同一模型时，按 key 升序的第一个绑定候选执行，与先前尝试固定了哪个候选无关。

每一次让插件投入服务的变更，都会针对当前的路由版本对该插件做预检：`enabled: true` 的上传（默认）、启用某个插件、激活某个版本（激活同时会启用它）、在另一个已存版本或出厂内置版本接管该 key 时删除当前激活版本，以及在出厂内置版本接管时再次以 `enabled: false` 上传正在服务的版本。被其他插件占用的渠道类型、仅大小写不同的模型名，或同一宿主路径与模型上的其他协议，都会拒绝该变更并保持原状（错误信息会指明对应的插件）；`force` 不能绕过该检查。在同一宿主协议或原生路径上共用模型是允许的。以 `enabled: false` 上传仍会存下这个冲突插件，而在其对应插件启用期间启用它会被拒绝。要替换某个插件，请先关闭旧的。

`endpoints`、`routes[].renderer`、全局 `resolveRequest`、全局 `renderError` 与全局 `renderers` 都被拒绝。`parseSubmitResponse` 只返回 `{taskId, taskData, immediate?, state?}`；`clientResponse` 被拒绝。

`icon` 是可选的 LobeHub 图标名字符串（例如 `Sora.Color`）。取值 `text` 与 `text:<label>` 表示改为生成文字头像（label 默认取 `name` 的前两个字符）。内联 data URI 与远程 URL 都被拒绝。`icon` 仅用于展示，不参与路由与计费。

供应商没有 LobeHub 图标的插件，把 logo 作为附属文件 `icon.svg` 或 `icon.png` 与 `plugin.js` 放在一起；清单保持可读，图片不会出现在源码 diff 中。内置插件从 `plugins/tasks/<key>/` 内嵌该附属文件。对于上传，管理界面读取文件并在上传请求的独立 `icon` 字段中以 `data:image/png;base64,...` 或 `data:image/svg+xml;base64,...` 发送；市场索引把它声明为 `iconFile.path`，安装器从索引自身的源获取它。网关把 logo 与源码分开存储，并通过 `GET /api/plugin/task/:key/icon`（可选 `?version=`）提供，界面只通过 `<img>` 渲染它。限制：512 KiB；PNG 必须带 PNG 签名；SVG 必须是格式良好的 XML，根元素为 `svg`，且不含 `script` 或 `foreignObject` 元素、事件处理属性、DOCTYPE、`javascript:` 取值或绝对的 `http(s)` 引用。请提供在浅色与深色背景上都清晰可辨的图稿（SVG 可以使用 `prefers-color-scheme` 媒体查询）。

`baseUrl` 是 type-61（"Task Plugin"）渠道的可选默认上游地址。当管理员绑定插件但把渠道 Base URL 留空时，宿主会在校验前把该值复制到渠道上，并在渠道审计事件中记录 `base_url_source: plugin_default`；此后每个请求都使用持久化后的渠道值，因此插件后续更新改变了 `baseUrl` 也不会迁移已有渠道。该值必须是绝对 `http` 或 `https` URL，不含凭据、查询或片段；主机部分会被转为小写且必须是 ASCII（国际化域名请用 punycode），尾部斜杠会被去掉，归一化后的值不得超过 191 个字符（MySQL 上渠道 `base_url` 列的宽度）。私有地址、回环地址与纯 `http` 地址对自建上游是允许的，管理界面会在绑定前给出提示。旧版 `channelTypes` 渠道会忽略 `baseUrl`，它们沿用按类型内置的默认值。默认主机不会隐式加入 `allowedHosts`：如果管理员把渠道指向另一个主机，插件发往作者默认主机的请求会被拒绝。

`allowedHosts` 列出除渠道 Base URL 主机之外，插件请求还可以访问的额外主机。这些主机在直接请求与任务查询重定向中都是可信的凭据接收方；只应加入被允许接收渠道凭据的主机。每个条目是 `host` 或 `host:port`（IPv6 字面量加方括号，例如 `[::1]:8080`）；协议、路径、凭据与查询都被拒绝。条目会被转为小写，归一化后必须唯一。带端口的条目只匹配该端口的请求（默认端口 `80`/`443` 匹配省略了端口的请求）。

`upstreams` 列出驱动的请求构造器可以访问的上游类型。`vendor` 是供应商 API 本身，每个插件都隐含支持它；`new_api` 是安装了同一插件的另一个 New API 网关。只有声明了 `new_api` 的插件才能绑定到 type-60 New API 渠道：保存渠道时宿主会拒绝其他绑定，渠道表单也只列出声明过的插件。网关只在该插件自己的原生路由上提供插件的线格式，并用 `Authorization: Bearer <token>` 鉴权原生路由与宿主协议。两个内置插件的原生路由还接受供应商自己形式的 token：vidu 的是 `Authorization: Token <token>`，google 的是 `x-goog-api-key: <token>` 或 `?key=<token>`。优先使用请求头：查询字符串会进入网关前置代理的访问日志。网关会在任何插件钩子看到之前把 `key` 从 URL 中取出，并且不把它写进自己的请求日志。客户端发送的 `Authorization` 请求头优先于上述两种 Gemini 形式。Kling 的 AK/SK JWT、Vertex AI 的 OAuth access token 与火山引擎 V4 签名都不接受。内置插件声明其供应商的官方路径，网关也在 `/{key}` 下提供它们（`/doubao/api/v3/...`、`/kling/v1/videos/...`）；alibaba 与 sunoapi 另外保留 `/ali/...` 与 `/suno/...`。较早版本的网关只在各自前缀下提供内置插件。因此宿主通过 `ctx.upstream` 告知驱动执行渠道的上游类型（见「持久化数据与驱动钩子」），而不是从 `meta.routes` 猜测前缀；供应商路径已等于其原生路由的插件（sunoapi），或只使用宿主协议的插件（sora），声明 `new_api` 而无需改动任何 URL。取值必须唯一，且只能取自上述两种类型；列出 `vendor` 是可选的、仅作说明。这是 apiVersion 1 的增量扩展：旧宿主会拒绝这个未知字段，而声明了它的插件在从不设置 `ctx.upstream` 的宿主上仍照常构造供应商 URL。

`channelTypes` 列出该插件的驱动可以驱动的旧版渠道类型（例如 sora 声明 `[55, 1]`，因为同样的 OpenAI 类型 Base URL 与 bearer key 同时服务于 chat 与 video）。每个条目同等参与渠道选择、历史 `Task.Platform` 匹配与 `byChannelType` 路由索引；同一个类型值不得出现在两个插件上，且不得声明 Task Plugin（61）与 New API（60）类型。第三方插件通常省略 `channelTypes`，通过 `task_plugin_key` 绑定到 type-61 的 "Task Plugin" 渠道，或被列在 type-60 New API 渠道的 `task_extend_plugin_keys` 中而不占用渠道类型。此前用于区分身份／兼容性的字段名已被拒绝。

在共享的宿主端点上，普通中转渠道与匹配的插件渠道按常规的分组、优先级、权重、亲和性与渠道固定规则竞争。插件的模型声明不会排除服务同一模型的普通 OpenAI 兼容渠道。当普通渠道胜出时，宿主保留原始请求体，并跳过插件模式检查、解码器与模型改写。该端点的重试仍留在普通渠道上；插件重试仍留在其被接受的插件候选上。插件拥有的原生路由保持其独占路由。

当插件渠道在初次选择中胜出时，宿主在最终分发之前会调用每个模式兼容候选的 `decodeRequest`。只有为固定模型返回有效提交意图的候选才继续有资格。如果全部拒绝该请求，宿主返回各候选的失败信息，并把相同的消息与给出它们的插件 key 归组。单个候选保留其原始失败信息。渠道选择之后，实际执行的插件会再次解码以构造自己的规范化请求。因此解码器必须容忍重复调用。渠道类型归属权仍然唯一；共用模型不会放宽这条规则。

共享模型可以为每个插件使用不同的用量 schema 与价格。管理员可以在 `billing_setting.plugin_billing_expr` 中保存一份供应商表达式，以 `<pluginKey>::<model>` 为键。没有覆盖时，供应商继承模型级表达式。如果生效的表达式引用了某个字面量 `u()` 键，而该键不在该供应商选定的 schema 中，那么该共享模型对该供应商就是未配置的；提交会以 400 `model_price_error` 失败，直到保存兼容的定价。定价页面会展示各供应商变体及其配置状态。模型级的用量标签继续取自 key 升序中的第一个插件。保存模型表达式时会检查同一草稿中每个没有自己覆盖的候选。供应商覆盖不参与模型价格同步。

当同一模型同时使用普通中转渠道时，把普通定价保留在模型级，把任务定价放进插件覆盖。普通中转表达式不能调用 `u()`；按张计价的美元价格请用 `fixed(...) * image_count`。任务表达式直接返回美元，而普通表达式保持其「美元乘以一百万」的结果契约。普通请求如果遇到用量表达式，或遇到该端点的任务插件仍在继承的表达式，会在预留或提交上游之前以 400 `model_price_error` 失败。含 `fixed()` 的表达式无歧义地属于普通定价，因为任务用量计费本就拒绝它们。既有任务表达式绝不会被自动改写或转换。

即使只剩一个供应商，已保存的覆盖依然可见且生效。覆盖所属插件不可用、或不再声明该模型时，会在管理快照中标记为 `stale`。其未变的值可以在保存其他价格时保留，也可以显式移除；新增或修改覆盖仍然需要当前有效的插件／模型绑定。公开变体会区分 `ratio` 回退定价与 `tiered_expr`，因此使用已配置按次价格的供应商不会仅因为没有表达式而被标记为未配置。

数值型 `usageSchema` 字段声明一个宿主拥有的单位：`second`、`count`、`token` 或 `credit`。布尔型字段声明 `{type: "boolean"}`。

带 `unit: "count"` 的数值字段还可以声明 `unitLabel`，即一个可选的 LocalizedText 展示单位。这能在不改变规范单位、用量事实、表达式键、价格或结算的前提下区分被计数的对象：

```js
image_count: {
  type: "number",
  unit: "count",
  unitLabel: {en: "image", zh: "张", "zh-TW": "張"},
  description: {en: "Image generation unit price", zh: "图片生成单价"},
}
```

标签是简短的单位名或计数词，例如 `image` / `张`、`song` / `首`，不含价格、数量、斜杠或结尾标点。它们与字段描述遵循相同的语言环境归一化、必需的英文回退，以及每个语言环境 256 rune 的限制。裸字符串会被归一化为英文 map。界面按当前语言、其主语言、然后英文的顺序选择；省略标签时保留宿主既有的计数单位展示。

标签是插件数据，不是前端翻译键。它们对 `usageSchema` 与 `usageProfiles[].schema` 同等适用，包括定价、计算器、插件详情与用量日志定价。其他单位、布尔值与枚举不能声明 `unitLabel`；token 价格保持其每百万的展示量级。

这是插件 API 版本 1 的增量扩展。升级后的宿主无需改动即可接受既有插件；旧宿主会拒绝未知的 `unitLabel` 属性。请先升级宿主，再安装声明了它的插件。

`meta.usageExamples` 是可选的、仅用于展示的定价示例列表。每个 `label` 是人类可读的规格名。每个 `facts` 对象必须是 `usageSchema` 上的完整向量：所有已声明的键都在、没有未声明的键，且取值通过与用量事实相同的校验。schema 中含 `unit: "token"` 数值字段的插件必须至少声明一个示例。示例绝不影响计费。标签是规格名（如 `std · 10s`），不是商城价格。

宿主在计算额度前会限定每一个用量事实，并且不从请求中读取计费数量。数值事实必须有限且非负，`second` 事实最多 3600，`count` 事实最多 128；`token` 与 `credit` 事实在 2,147,483,647 处饱和。违反这些规则的提交事实在计费前会让请求以 400 失败。插件自行校验自己的请求：它从自己发往上游的请求推导事实，包括从 `metadata` 或其他透传 map 合并进来的值，并限定任何被它转成 `token` 或 `credit` 事实的请求数量，因为宿主只对这两类做饱和。转发时长为 `-1` 的插件（某些供应商把它读作「由模型决定长度」，如火山方舟的 Seedance、百炼的 wan3.0）必须预留该模型可产出的最长时长，并按供应商上报的用量结算任务。

### 按模型划分的用量档案

`meta.usageProfiles` 可选地包含 `{models, schema, examples?}` 条目。每个档案为自己的模型提供完整 schema 与展示示例，替换掉 `usageSchema` 与 `usageExamples`，不做合并也不继承。未匹配的模型使用插件默认值。模型必须使用 `meta.models` 中声明的拼写，且最多属于一个档案。空的模型列表与缺失／null 的 schema 会被拒绝；空的 schema 对象是合法的。token 单位的档案需要自己的示例。档案内部适用与插件层级相同的字段、描述与示例校验。

按用例定义常量（例如 `IMAGE_USAGE_SCHEMA` 与 `VIDEO_USAGE_SCHEMA`），再从档案中引用它们。这些都是普通的 JavaScript 常量：宿主在读取 `meta` 之前先执行模块。静态消费方可以使用市场索引中编译好的展示元数据。

模型级定价与保存校验会选择别名的声明目标；有歧义的别名保留插件默认值。运行时校验选择实际执行插件的最终上游模型，包括批量轮询期间的每个持久化任务；当没有档案声明该上游名时（例如渠道映射把已声明的模型发送到供应商端点 ID），适用面向客户端的模型所属档案。既有已保存的表达式不会被迁移。单插件模型保留其既有的提交检查；共享模型还会额外强制上面那条按供应商的字段引用兼容性规则。常规求值与额度安全检查继续生效。保存表达式时使用其模型选定的 schema；单插件模型在档案收窄之后，未变更的已存表达式仍可保存。插件从档案中去掉某个事实时，仍要以不改变既有费用的取值上报它：`0`、`false`，或最先声明的枚举值。定价编辑器以同样方式读取已存表达式，并只显示剩余字段。

这仍属于插件 API 版本 1。新宿主可原样接受旧插件；旧宿主会拒绝新的 `usageProfiles` 字段。请先升级到支持档案的宿主版本，再安装声明了它们的插件。

## LocalizedText

`meta.description` 与每个 `usageSchema` 字段的 `description`、`unitLabel` 都接受 LocalizedText。裸字符串等价于 `{en: <string>}`。map 必须包含非空的 `en` 取值。宿主把两种形式都归一化为 map；API 响应始终输出对象。

枚举字段还可以声明 `enumLabels`，即从枚举取值到 LocalizedText 展示名的 map：

```js
video_input: {
  enum: ["none", "video"],
  description: {en: "Reference video input", zh: "参考视频输入"},
  enumLabels: {
    none: {en: "No reference video", zh: "无参考视频"},
    video: {en: "With reference video", zh: "有参考视频"},
  },
}
```

`enumLabels` 可选，且可以只覆盖部分选项。它只在枚举字段上有效，每个键必须与已声明的枚举取值完全一致。每个标签与字段描述遵循相同的语言环境归一化、必需的英文回退与每个语言环境 256 rune 的限制。标签是简短短语，不带结尾标点。它们绝不改变用量事实、表达式条件或界面控件提交的取值。布尔字段使用其描述配合本地化的「是／否」状态，不能声明 `enumLabels`。

界面按当前语言、其主语言、然后英文的顺序选择。若没有提供选项标签，则展示原始枚举取值；字段描述缺失时回退到字段名。标签是插件数据，不是前端翻译键。

这是 `apiVersion: 1` 的增量扩展。升级后的网关继续能加载不带 `enumLabels` 的插件；带严格属性校验的旧网关会拒绝声明了它的插件。

```js
description: "Video generation via the vendor API"
description: {en: "Video generation via the vendor API", zh: "通过厂商接口生成视频"}
```

规则：

- 语言环境键匹配 `^[a-zA-Z]{2,3}(-[a-zA-Z0-9]{2,8})*$`。一个 map 最多 16 个语言环境。
- 键会被规范化为 BCP-47 大小写（`EN` → `en`，`zh-tw` → `zh-TW`，`zh-hans` → `zh-Hans`）；规范化后冲突的两个键作为重复项被拒绝。
- 每个取值都会被去除首尾空白，必须非空，且不含控制字符。
- `meta.description` 每个语言环境最多 512 个 rune。每个 `usageSchema` 字段的 `description` 每个语言环境最多 256 个 rune。
- 前端按精确标签 → 主子标签 → `en` 的顺序解析语言环境（例如 `zh-TW` → `zh` → `en`）。
- 任何语言的描述文案都不得包含供应商的货币价格。同样的禁止也适用于 `usageExamples` 的标签。

### 描述撰写与翻译约定

描述是面向用户的简短短语，任何语言都不带结尾标点。各语言翻译保持含义等价。`usageSchema` 字段请使用以下措辞：

| 字段含义 | 措辞 | 英文示例 | 中文示例 |
| --- | --- | --- | --- |
| 数值型计费数量 | 计费主体 + 单价 | Song generation unit price | 生成歌曲单价 |
| 动作 | 动作短语 | Generate songs | 生成歌曲 |
| 布尔值 | 是否启用某状态或某物是否存在 | Whether audio is generated / Reference video present | 是否生成音频 / 存在参考视频 |
| 其他枚举条件 | 简短条件名 | Output video resolution | 输出视频分辨率 |

- 共享的描述必须覆盖所有受支持的动作。对 Suno，`clips.description` 为 `Song or lyrics generation unit price` / `生成歌曲或歌词单价`，`action.description` 为 `Generate songs or lyrics` / `生成歌曲或歌词`。
- 布尔描述要指出 `true` 所代表的肯定状态；不要加问号，也不要反转字段含义。
- 保留诸如「输入」与「输出」这类区别。单位放在 `unit` 中；不要在描述里重复单位说明或具体价格。
- 协议限制、用量来源、估算与结算细节应放在代码注释或技术文档中，而不是展示描述里。
- 例如，把 `Requested video duration in seconds.` / `请求的视频时长，单位为秒。` 换成 `Video generation unit price` / `视频生成单价`；把 `Whether audio is generated. Default true.` / `是否生成音频。默认为 true。` 换成 `Whether audio is generated` / `是否生成音频`。
- 这些是针对插件元数据的编写约定，不是额外的运行时校验规则。既有的 `LocalizedText` 线格式、用量数量、枚举取值与计费语义都不变；数值字段仍然承载用量，而不是价格。

## 宿主工具与能力

`utils` 暴露同步的宿主工具。现有工具包括 `unixNow`、`uuid`、`hmacSHA256`、`jwtSignHS256`、`base64`、`base64URL`、`base64URLDecode`、`volcSignV4`、`json.clone` 与 `fetch`；它们的签名声明在 `v1.d.ts` 中。

宿主根据插件导出或返回的内容识别一项能力，例如导出的 `parseSubmitEventDelta`。插件只有在要开启某种会改变钩子所收到内容、或放宽某项宿主检查的行为时才声明能力：

```js
requiredCapabilities: ["json-order@1"]
```

宿主在加载时拒绝未知、重复或不受支持的 capability 版本。省略该字段保持既有行为。`utils.hasCapability(name)` 在提供该工具的宿主上支持可选的特性探测；它并不授予已声明的能力。这些都是 API v1 的增量扩展；严格的旧宿主会拒绝 `requiredCapabilities`，因此请先升级宿主。

`json-clone@1`、`submit-sse-delta@1` 与 `duration-auto@1` 仍被接受，以兼容为早期宿主编写的插件；新插件不需要其中任何一个。`json-clone@1` 与 `duration-auto@1` 已无效果。`submit-sse-delta@1` 仍要求 `submitResponseTypes` 包含 `sse` 且插件导出 `parseSubmitEventDelta`。

`utils.json.clone(value)` 返回一份独立的 JSON 快照，其中含有原生的可变 JavaScript 对象与数组。它接受普通对象、数组、null、布尔值、有限数值与字符串。undefined、函数、BigInt、日期、稀疏数组与循环结构都被拒绝。像 `__proto__` 这样的对象键仍是普通自有数据属性。该工具使用宿主的 JSON 数值与字符串归一化，并保留显式的零值与 false。限制为：编码后 JSON 1 MiB、根以下 32 层、合计 32,768 个节点（含容器与标量）。它不执行任何 I/O。

`json-order@1` 为把 JSON 成员顺序视为有意义的上游保留该顺序，例如把 JSON 对象当作文本读取的模型。插件的解码器收到 JSON 请求体（`ctx.body.value`），其驱动钩子收到已解码的 `ctx.requestBody`，成员顺序与客户端发送的一致；宿主按 `JSON.stringify` 的方式写出插件的 JSON 请求描述符负载：成员按插件对象中持有的顺序、值为 `undefined` 的成员被省略、不做 HTML 转义。与 JavaScript 一样，数组索引形式的键排在最前并按升序。没有该能力时，对象到达钩子时成员按键排序，宿主 JSON 编解码器也按键排序写出负载。每个解码器与驱动钩子调用都会重新解析有序负载，在大负载上开销更高，因此只在确实需要时才声明该能力。内嵌文件占位符的负载仍按排序写出。

宿主函数是同步的，必须自行限定工作量：JavaScript 执行中断无法抢占正在运行的 Go 函数。请求作用域的数据必须由宿主请求持有，而不是由池化的运行时全局变量持有。`utils.fetch` 等待网络时不占用 JavaScript 执行槽位，该等待不计入钩子的执行时间。

### 用 utils.fetch 读取上游数据

```ts
utils.fetch(request: {url: string; method?: "GET" | "HEAD"; headers?: Record<string, string>; responseType?: "json" | "bytes"}):
  {status: number; headers: Record<string, string>; body: JSONValue | string | ArrayBuffer}
```

`utils.fetch` 让驱动钩子在返回前读取上游数据，例如供应商只通过单独查询才给出的下载链接。该调用是同步的。请求取自请求描述符的 `url`、`method` 与 `headers` 成员；结果的形态与 `parseTaskResult` 收到的响应一致：HTTP 状态码、每个响应头在其规范名称下的首个取值（`Content-Type`、`Location`），以及负载。

- 当响应能解析为 JSON 时（`JSON.parse` 语义），`body` 是解析后的 JSON，否则是文本。`HEAD` 响应的 body 是空字符串。
- `responseType: "bytes"` 会把 `body` 改为响应字节的 `ArrayBuffer`，用于二进制数据，例如用 `Range` 请求头读取的媒体文件头；`HEAD` 响应是空 buffer。负载上限相同。
- 该 URL 可以指向与请求描述符相同的主机：渠道 Base URL 主机与 `allowedHosts`。
- 请求使用轮询请求所用的客户端与渠道代理。
- 不跟随重定向。3xx 响应原样返回；获取其 `Location` 是一次新请求，会再次被检查与计数。
- HTTP 错误状态码会被返回，而不是抛出。
- 限制：每次钩子调用最多 4 次 fetch，每次 fetch 15 秒，一次钩子调用的所有 fetch 合计 30 秒，每个响应负载 1 MiB。

`utils.fetch` 在下列情况下抛出异常：

- 该钩子不允许 fetch（见下文）；
- 请求包含 `url`、`method`、`headers` 与 `responseType` 之外的成员；
- 方法不是 `GET` 或 `HEAD`（默认 `GET`），或 `responseType` 不是 `json`（默认）或 `bytes`；
- URL 不是绝对 `http(s)` URL，或超过 64 KiB；
- 请求头超过 64 个、某个头的值超过 8 KiB，或请求头为 `Host`、`Content-Length`、`Accept-Encoding`、`Connection`、`Proxy-Connection`、`Keep-Alive`、`Proxy-Authorization`、`TE`、`Trailer`、`Transfer-Encoding` 或 `Upgrade`；
- 主机不在允许列表内；
- fetch 超时，或本次调用用完了 fetch 次数或 fetch 时间；
- 响应负载超过 1 MiB；
- 传输失败。

钩子错误会到达 API 调用方，因此这些消息只提到宿主，绝不提到路径或查询串。

Fetch 是只读的。会触发计费供应商工作的请求必须留在 `buildSubmitRequest` 描述符中 —— 那是网关唯一会计的请求。`utils.fetch` 只在渠道选择之后运行、且失败无害或可重试的驱动钩子中可用：`buildSubmitRequest`（提交并未发出）、`buildQueryRequest`、`parseTaskResult`、`buildBatchQueryRequest` 与 `parseBatchResult`（一次失败的轮询），以及 `buildContentRequest`（一次失败的下载）。其他所有钩子，以及没有渠道的 dry run，都会抛出 `utils.fetch is not available in <hook>`。没有该工具的宿主上没有 `utils.fetch`；在那里调用会抛出 `TypeError`，钩子像其他钩子错误一样失败。它不需要声明能力。

## 钩子参数与返回值

宿主把纯 JSON 值传给钩子而不做拷贝：对象、数组、字符串、有限数值、布尔值与 null。引擎在钩子首次读取时转换每个对象或数组，绝不把 JavaScript 的改动写回宿主值。其他值（结构体、字节切片、`json.Number`、原始 JSON、非法 UTF-8、非有限数值、nil 切片，或嵌套超过 64 层）会先通过宿主 JSON 编解码器归一化。

插件规则：

- 把每个参数都当作只读输入。给参数赋值只改变本次调用的视图；宿主、其他钩子与后续调用都看不到它。返回宿主应当使用的值，需要可变副本时使用 `utils.json.clone`。
- 钩子返回后，不要把参数、或从中读到的对象与数组，保存在模块变量里。运行时会在请求之间池化，所以被保留的值可能出现在后续请求中，让原始请求的数据一直存活，并且仍然是从宿主值读到的。

宿主规则：

- 一个值传给钩子之后，宿主代码不得修改它。插件仍可能持有它，而在另一个 goroutine 写入时读取 Go map 是 `recover` 无法捕获的致命运行时错误，会终止整个进程。请构造新值，或先复制（任务适配器中的 `jsonValue` 会复制纯 JSON 并归一化其他一切）。
- 钩子返回值可以是宿主值。原样返回某个参数或其一部分的钩子，交回的是原始宿主值而不是副本。因此在原地修改返回值之前要先复制 —— 请求描述符的文件占位符正是出于这个原因才在副本上替换。
- JavaScript 创建的整数回来是 `int64`，其他数值是 `float64`；原样返回的宿主值保留其原有 Go 类型。从钩子结果读取数值的代码必须接受所有数值类型，而不是断言为 `float64`。两种情况下 JSON 编码相同。

## 请求体

每个解码器收到一个由宿主解析的请求体：

```ts
{kind: "json", value}
{kind: "form", fields: Record<string, readonly string[]>}
{kind: "multipart", fields: Record<string, readonly string[]>, files: readonly FileReference[]}
{kind: "none"}
```

JSON 的 `value` 按键枚举其对象成员；对于声明了 `json-order@1` 的插件，则按客户端的顺序。

原生 `submit` 与 `dynamic` 路由接受 JSON 与 multipart 请求体；其他媒体类型与空请求体在解码器运行之前就以 415 拒绝，`query` 路由不接受请求体。声明了 `models` 的路由只接受 JSON，因为宿主要从 JSON 请求体读取模型。解码器应拒绝其供应商格式不使用的请求体类型，通常给出 `JSON body required`。本扩展之前发布的网关在原生路由上只接受 JSON。

`FileReference` 包含 `{ref, field, filename, mimeType, size}`。ref 是不透明的、请求作用域的；文件字节、读取器、临时路径以及第二份入站 `requestBody` 表示都绝不暴露给 JavaScript。每个上传的文件都有自己的 ref，包括同一重复字段中的多个文件（`image[]`）：该字段的第一个文件是 `request_file:<field>`，之后的文件是 `request_file:<field>#<index>`，索引从 0 开始。插件应复制 `files[].ref`，而不是手写 ref。解码器创建一份新的规范意图 `{kind:"submit", model, action?, requestBody?, originTaskIds?}`。驱动钩子消费该规范化后的 `requestBody`，并与传输表面无关。

## 请求构造

渠道的 **请求头覆盖** 设置在提交、查询、批量查询与带凭据的内容请求中，作用于描述符请求头之后，并替换同名的描述符请求头。`{api_key}` 是该请求用于鉴权的密钥。透传规则与 `{client_header:NAME}` 只作用于提交。内容请求保留其 URL 的主机；无凭据的内容请求与 `utils.fetch` 按插件构造的方式发送。无效的请求头取值会让请求失败。

`buildSubmitRequest` 返回一个请求描述符。JSON 请求体（默认）可以在任意对象或数组深度内嵌文件占位符。宿主在请求发出前把每个占位符替换为编码后的字符串；JavaScript 永远看不到文件字节。

```js
{ __fileRef: "request_file:input_reference", encoding: "base64" }                 // 原始 Base64
{ __fileRef: "request_file:input_reference", encoding: "dataUrl" }                // data:<mime>;base64,<data>
{ __fileRef: "request_file:input_reference", encoding: "dataUrl", mimeType: "image/png", maxBytes: 20971520 }
```

占位符对象只能包含 `__fileRef`、`encoding`、`mimeType` 与 `maxBytes`。`encoding` 是 `base64` 或 `dataUrl`。`__fileRef` 必须解析到一个已上传的 multipart 文件（`request_file:<field>`，或重复字段后续文件的 `request_file:<field>#<index>`）。`mimeType` 可选，用于覆盖 `dataUrl` 的分段 `Content-Type`（否则用分段头，再否则用 `application/octet-stream`）。`maxBytes` 是可选的供应商上限；宿主还会对每个文件以及内联字节总量应用 `MAX_FILE_DOWNLOAD_MB`（默认 64MB）。multipart 描述符仍通过 `parts[].fileRef` 流式发送文件。

宿主把每一个 2xx 上游状态（`200`、`201 Created`、`202 Accepted` 等）都视为提交成功，并用 `{statusCode, headers, body}` 调用 `parseSubmitResponse`；其他任何状态都会在钩子运行之前以该上游状态与请求体让提交失败。

当上游把产物内嵌在 JSON 应答中而不是作为应答本身返回时，`buildContentRequest` 可以返回 `contentPath`，正如 Vertex AI 的 `fetchPredictOperation` 返回内联视频那样：

```js
{url, method: "POST", headers, body: {operationName}, responseType: "json",
 contentPath: ["response", "videos", 0, "bytesBase64Encoded"], mimeType: "video/mp4"}
```

该路径遵循 JSON 变更路径的规则：字符串键与非负整数索引，最多 32 段。宿主把 200 应答视为一个长时间运行的操作：含 `error` 成员的应答回答 502 `artifact_upstream_error`，既不是 `done: true` 也不是带 `status: "completed"` 的交互的应答回答 409 `artifact_not_ready`，`contentPath` 处的取值不是非空字符串则回答 410 `artifact_gone`。否则它把该字符串按 base64（标准或 URL 安全）解码，并以 `mimeType`（默认 `video/mp4`）作为 `Content-Type` 提供字节；HEAD 客户端只拿到响应头。应答不得超过 `MAX_FILE_DOWNLOAD_MB` 的四分之三再加 1 MiB（502 `artifact_request_rejected`），且这类请求不会带上客户端的 range 与校验器请求头。其他状态保持常规映射。提供产物期间整个应答都驻留在内存中。其他钩子忽略 `contentPath` 与 `mimeType`。

## 起始任务

解码器把供应商引用（草稿 id、续写 id、网关签发的资产引用）归一化为 `originTaskIds`，即公开的网关任务 ID。宿主绝不解析供应商请求体。

宿主会校验归属权，要求每个被引用的任务都属于同一插件平台集合与同一个已启用渠道，为该提交固定该渠道（包括重试），并把解析出的行作为 `ctx.originTasks`（`taskId`、`upstreamTaskId`、`action`、`status` 与 `data`，含私有上游 id）注入驱动钩子。提交路由声明了 `retainResult: false` 的任务，其 `data` 为 `null`。渲染器与呈现器永远收不到 `originTasks`。

## 原生表面

```js
export const native = {
  createJob(ctx) { return {kind: "submit", model: ctx.body.value.model, requestBody: ctx.body.value}; },
  jobCreated(ctx, task) { return {job_id: task.task_id, state: "queued"}; },
  jobStatus(ctx, task) { return task.data; },
  error(ctx, error) { return {code: error.code, message: error.message}; },
};
```

宿主负责鉴权、校验归属权、持久化任务、构造 `TaskView`，并在调用呈现器之前把已知的私有任务 id 字段替换为公开 ID。原生呈现器拥有供应商的外层信封。带鉴权的原生查询呈现器可能有意透传来自 `task.data` 的供应商 URL。

原生呈现器的返回值是 200 应答的 JSON 请求体；错误呈现器的返回值是带宿主状态码的应答体。必须以供应商自身状态码作答的呈现器改为返回一个应答包装器，通过它的 `__status` 成员识别：

```js
{__status: 202, __body: {status: "pending", progress: 40}}                 // xAI 的待处理视频
{__status: 200, __body: {request_id: "...", output: {task_status: "UNKNOWN"}}} // DashScope 的未知任务
{__status: 302, __headers: {Location: url}}                                 // 无 __body：即无请求体
```

`__status` 是 200 到 599 之间的整数。`__headers` 只能设置 `Location` 与 `Retry-After`，且必须是字符串。含有其他成员、或取值无效的包装器会让呈现器失败（查询返回 500，提交使用宿主回退，错误呈现器使用脱敏后的宿主错误）。这适用于原生路由上的提交、查询与错误呈现器；宿主协议保持其状态码。

查询呈现器会收到 `ctx.artifacts`，与 Responses 渲染器相同：对于一个处于 `SUCCESS` 且其插件导出了 `listArtifacts` 的任务，为 `{key: {key, type, url, mimeType?}}`，每个 `url` 都是一个签名过的网关地址，无需凭据即可下载产物；其他情况为 `{}`。对任务列表同理。抛出 `artifact_not_found` 的呈现器会像任务不存在一样回答（404）。hailuo 就是这样回答 MiniMax 的 `GET /v1/files/retrieve?file_id=`：它的 v1 查询把任务 id 报为 `file_id`，而 retrieve 响应中的 `download_url` 就是该视频的网关地址。

## 错误契约

钩子的 `Error` 消息会被（截断并脱敏后）呈现给 API 调用方。插件作者应把校验失败写成用户可读的句子。

## 宿主协议

宿主注册表拥有以下绑定：

| 协议 | 操作 | 绑定 | 请求体 |
| --- | --- | --- | --- |
| `openai_responses` | create | `POST /v1/responses` | JSON |
| `openai_responses` | retrieve | `GET /v1/responses/:response_id` | 无 |
| `openai_video` | create | `POST /v1/videos` | JSON 或 multipart |
| `openai_video` | retrieve | `GET /v1/videos/:task_id` | 无 |
| `openai_video` | content | `GET \| HEAD /v1/videos/:task_id/content` | 无 |
| `openai_image` | generate | `POST /v1/images/generations` | JSON |
| `openai_image` | edit | `POST /v1/images/edits` | JSON 或 multipart |

`protocols.openai_responses` 始终需要 `decodeRequest`。其余钩子由 `supports` 推导，并在加载时双向精确校验：`"stream"` 需要 `renderEvents`；`"sync"` 或 `"background"` 需要 `renderFinal`。某个受支持模式所要求的钩子没有导出，或导出了没有任何受支持模式使用的钩子，都会拒绝该插件。只支持 `"stream"` 的插件，其获取在终态 SUCCESS 时由宿主调用一次没有先前状态的 `renderEvents` —— 这与流式本来就要求的「终态首次调用」语义相同。模式词汇表在 apiVersion 1 下只增不减：可以新增模式（既有清单不受影响；声明了某个模式的清单只在定义了该模式的网关上加载），但未经 apiVersion 提升，绝不可移除、重命名或重新映射到不同钩子。`protocols.openai_video` 的 create 需要 `decodeRequest`，retrieve 需要 `render`。宿主提取并固定 `ctx.model`，归一化 `ctx.stream`，组织 SSE 帧，构造失败信封，并仅对 `SUCCESS` 调用 `renderFinal`。

create 上的 `background: true` 会立即返回待处理的 Response（由宿主合成，不经插件钩子）。获取仅在终态时通过 `renderFinal` 渲染。声明 `"background"` 的插件不需要 create 阶段的钩子；交付物在获取时通过 `renderFinal` 渲染。插件无法观察 `background` 字段。与上游 OpenAI API 不同，未声明 `"stream"` 的插件会以 400 拒绝 `stream: true`；错误信息会指出受支持的形式。

`protocols.openai_image` 需要 `decodeRequest` 与 `render`，且不定义任何模式。从客户端视角看，两个操作都是同步的。宿主提取并固定 `ctx.model`（`ctx.operation` 为 `generate` 或 `edit`），解码器返回常规的提交意图，而 `buildSubmitRequest` 与原生路由一样针对供应商运行。同步应答的供应商从 `parseSubmitResponse` 返回终态 `immediate`；供应商任务 API 则返回任务 id，随后宿主在客户端请求内通过与后台轮询器相同的查询钩子与完成结算（`buildQueryRequest`、`parseTaskResult`、`extractUsageOnComplete`）轮询该任务，每隔数秒一次，直到任务进入终态或协议超时（`TASK_PLUGIN_PROTOCOL_TIMEOUT_SECONDS`，默认 600 秒）到期。超时时客户端收到 504 `task_timeout`；任务仍然持久化，并在轮询器完成时结算。客户端在等待期间断开也同样把任务交给轮询器。终态 `FAILURE` 以 400 回答，并带上任务的失败原因。在 `SUCCESS` 时，宿主用请求上下文与终态 `TaskView` 调用 `render(ctx, task)`；该钩子必须返回一个对象，其 `data` 是 OpenAI 图片条目的数组（`{url}` 或 `{b64_json}`，可选 `revised_prompt`）。宿主在缺失时补上 `created`，并掌管 `response_format`：对 `b64_json`，它会下载每个 `data[].url` 并补上 `b64_json`（URL 保留；下载失败记录警告并保留 URL）。`render` 收不到 `artifacts`；图片 URL 来自供应商结果。计费遵循常规的任务契约：按 `extractUsage` 的请求数量预留，按 `extractUsageOnSubmit`（立即结果、旧版定价）与 `extractUsageOnComplete`（立即结果与轮询结果、任务表达式）的实际数量结算；当事实中带有 `image_count` 时，消费日志把计费数量记录为 `other.image_count`。

Responses 协议的媒体使用宿主注入的 `ctx.artifacts[key].url`。OpenAI Video 渲染器可以返回来自 `task.data` 的供应商字段与 URL；宿主保留这些扩展与元数据，但会覆写 `id`、`object`、`model`、`status`、`progress`、`created_at` 与 `completed_at`，并移除旧版 `task_id`。渲染器必须返回 JSON 对象。返回 `task.data` 会暴露最近一次持久化的上游快照，受宿主的任务 ID 替换与内联视频脱敏约束；它不会发起新的上游查询，也不会转发 HTTP 头／状态码。

## 持久化数据与驱动钩子

持久化字段仍是 `task.data`；没有 `task.raw` 别名。驱动钩子（`buildSubmitRequest`、`parseSubmitResponse`、查询／结果、用量、产物与内容钩子）保持扁平，不得按客户端路径或协议分支。

`ctx.model` 是计费与展示身份（客户端发送的原始名称，含渠道映射别名）。`ctx.upstreamModel` 是渠道 `model_mapping` 之后的机器身份。费率表与以模型为键的用量事实必须使用 `ctx.upstreamModel || ctx.model`。回显客户端模型的解码与渲染钩子必须保留 `ctx.model`。在映射固定的场景下，`buildSubmitRequest` 不得设置描述符顶层的 `model`；宿主要求插件逐字回显该别名。后台轮询没有中转信息，因此查询钩子从持久化的任务属性中获得两个身份，当任务提交时没有渠道映射，`ctx.upstreamModel` 回退到 `ctx.model`。

`ctx.upstream` 在 `DriverContext`、`TaskQueryContext`、`BatchQueryContext` 与 `buildContentRequest` 上下文中是 `{kind: "vendor"}` 或 `{kind: "new_api"}`，提交与后台轮询皆然。`new_api` 表示执行渠道是 type-60 的 New API 渠道，由上游网关上的同一插件作答。此时驱动会给它构造的 URL 加上自己的原生路由前缀（doubao `/doubao`、alibaba `/ali`、kling `/kling`），这是每个网关版本都提供的形式；jimeng 在那里调用 Jimeng 的 Bearer API，即 `/jimeng/api/common/v3/submit_task_v2` 与 `get_result_v2`，较早的网关不提供这些。宿主已经为每种 `meta.auth` 类型把 `authHeader` 设为 `Bearer <channel key>`、`apiKey` 设为渠道密钥：New API 渠道的渠道密钥就是网关 token，因此供应商的鉴权方案（`oauth2_jwt` token 交换、由 `ak|sk` 构建的供应商 JWT）不会执行。使用 `vendor` 时一切不变。驱动读回的响应，就是它自己的原生呈现器在网关上渲染的内容，而宿主已把 `id` / `task_id` / `taskId` 字段中的私有上游 id 替换为网关的公开任务 id；`parseSubmitResponse` 必须接受该形态，查询 URL 必须能以该 id 在插件自己的 `query` 路由上解析。指向网关的旧渠道上，kling 与 jimeng 保留其 `sk-` 密钥前缀启发式；当显式信号表明是 `new_api` 时，以显式信号为准。`ctx.upstream` 是 apiVersion 1 的增量扩展；驱动必须把字段缺失视为 `vendor`。

`DriverContext` 上的 `ctx.requestHeaders`，以及原生与协议解码器上下文上的同名字段，保存客户端的请求头，每个请求头在其规范名称下的首个取值（`TypeSafe-Danger-Zone-Long-Context` 会以 `Typesafe-Danger-Zone-Long-Context` 到达），因此驱动可以大小写不敏感地比较名称。`Content-Type` 与 `Accept` 始终存在，客户端没发时为空。携带网关凭据的请求头（`Authorization`、`Proxy-Authorization`、`Cookie`、`X-Api-Key`、`X-Goog-Api-Key`、`Mj-Api-Secret`）会被剔除。宿主不会向上游转发其中任何一个；驱动只把其供应商定义的请求头复制进请求描述器。轮询上下文没有客户端请求，也不携带任何请求头。本扩展之前发布的网关只传 `Content-Type` 与 `Accept`，且不向解码器传任何请求头；读取供应商请求头的解码器（如 alibaba 读取 `X-DashScope-Sse`）需要一个会传递它们的网关。

## 轮询契约

查询与解析钩子使用 `TaskQueryContext`，而不是 `DriverContext`。宿主从持久化的任务行重建该上下文。查询侧没有 `requestBody`。

| 字段 | 来源 |
| --- | --- |
| `taskId` | 上游任务 id（`PrivateData.UpstreamTaskID`，否则 `TaskID`） |
| `publicTaskId` | 网关任务 id |
| `action` | 归一化后的持久化 action |
| `model` | `Properties.OriginModelName` |
| `upstreamModel` | `Properties.UpstreamModelName`，回退到 `model` |
| `baseUrl` / `apiKey` / `authHeader` / `auth` | 渠道凭据；在 New API 渠道上 `authHeader` 为 `Bearer <channel key>`，且每种鉴权类型的 `apiKey` 都是该密钥 |
| `upstream` | 来自执行渠道类型的 `{kind: "vendor" \| "new_api"}` |
| `data` | 当前 `Task.Data` 快照 |
| `state` | 插件自有的 `PrivateData.PluginState` |

`Task.Data` 是呈现器与产物所用的最近一次上游响应快照。宿主在每次成功解析后覆写它。需要跨轮次存活的值属于 `state`。

`parseSubmitResponse`、`parseTaskResult` 与每个 `parseBatchResult` 条目都可以返回可选的 `state`。宿主只在钩子返回它时才写入。省略 `state` 会保留先前的值。超限的状态会被拒绝并给出警告，而不是被截断。

`buildBatchQueryRequest(ctx, tasks)` 与 `parseBatchResult` 收到 `tasks: TaskQueryContext[]`。`parseTaskResult` / `parseBatchResult` 还会收到上游 HTTP 响应的 `{status, headers}`。

单任务与批量任务查询重定向与直接的插件请求使用同一套凭据边界：渠道 Base URL 主机与 `meta.allowedHosts`，沿用既有的精确主机与端口匹配。省略 `allowedHosts` 不授予任何额外主机。需要其他凭据接收方的插件把它加入这个既有的列表即可；不需要重定向选项或查询描述符字段。

越出该边界的重定向会继续请求，但不带原始请求头，`Accept` 与 `Accept-Language` 除外；`Referer` 与 URL 中的用户信息也会被移除。经过任何不可信跳之后，即使后续跳回到受信主机，凭据也保持移除。任意插件与渠道的凭据请求头都受此保护。307/308 只有沿受信链才能重放查询体；其他请求体重放会让该轮轮询失败，并走既有的轮询失败处理。

每次重定向仍要通过既有的 SSRF 检查与重定向链最多 10 次请求的限制。即使目标是允许的主机，HTTPS 到 HTTP 的重定向也被拒绝。可信主机内部的 HTTPS 升级是允许的。

`utils.fetch` 仍会向插件返回重定向。

`status: "UNKNOWN"` 表示插件无法识别该响应。不要为缺失的表项写 `|| "IN_PROGRESS"`（或等价写法）。宿主把 `UNKNOWN`、钩子错误、空状态与无法识别的状态字符串都视为连续轮询失败。

在采信非终态解析结果之前，宿主会先对 HTTP 状态分类：

| 上游 HTTP | 宿主动作 |
| --- | --- |
| 2xx | 调用解析钩子 |
| 404 / 410 | 立即 `FAILURE` 并退款 |
| 401 / 403 | 任务状态不变；`PollFailures` 加一；带渠道 id 记录 `LogWarn`。渠道不会自动禁用。 |
| 429 / 5xx / 传输错误 | `PollFailures` 加一 |
| 其他 4xx | 用 `response.status` 调用解析钩子。仍是非终态的结果属于无法识别，`PollFailures` 加一。 |

一次有效的 2xx 非终态解析会把 `PollFailures` 重置为 0。连续失败达到 `TASK_POLL_MAX_FAILURES`（默认 20）次后，任务变为 `FAILURE` 并走既有的退款链路。`TASK_TIMEOUT_MINUTES` 巡检（默认 72 小时，即 4320 分钟）仍是最外层的期限。

市场索引 v1 的插件条目也接受可选的 `sortPriority` 与 `website` 字段。每个来源独立排序，优先级降序、key 升序。缺失或无效的优先级回退为 `0`；无效的网址会被隐藏。已安装插件与渠道绑定选项使用插件元数据。官网链接只在用户交互时打开；宿主不会去获取它们。

## 立即完成与提交流

驱动可以从 `parseSubmitResponse` 返回 `immediate: {status: "SUCCESS" | "FAILURE", ...}`。立即成功时，宿主用一个 `TaskQueryContext` 调用既有的 `extractUsageOnComplete(ctx, result, taskData)`，带上两个模型身份、提交的任务 id、解析出的数据与返回的插件状态。与轮询相同的模型专属用量校验同样适用。插件返回用量数量，绝不返回宿主额度或费用。

对于任务表达式，宿主把有效的完成事实覆盖到冻结的提交事实上，求值冻结的表达式，并在持久化前预留任何增量。最终额度、用量与档位在单次 BillingSession 结算之前记录。零用量会被保留。无效事实或表达式求值失败会保留预留并产生警告。立即失败结算为零。终态任务不会被轮询。旧版按次定价保持其既有含义与提交比例钩子。

### 可选的 SSE 应答读取器

`meta.submitResponseTypes` 默认为 `["json"]`。需要 SSE 的插件要包含 `"sse"` 并导出 `parseSubmitEvent`，或为宿主托管的累加模式导出 `parseSubmitEventDelta`（见下文）。`buildSubmitRequest` 在其请求描述符上选择 `responseType: "sse"`（默认 `"json"`）；所选类型必须已声明。这个可选的 v1 清单字段需要宿主支持：严格的旧宿主会直接拒绝它，而不是错误地解读这条流。

```ts
parseSubmitEvent(ctx: DriverContext,
  event: {event: string; id: string; data: string},
  previousState: JSONValue | null
): {state: JSONValue; done: boolean}
```

宿主接受 `text/event-stream`，把多行 `data:` 用换行拼接，处理 CRLF、注释心跳、事件名（默认 `message`）与事件 ID。它不解析供应商 JSON、不解释供应商的完成标记、也不汇总用量。这些由插件完成，并在每次调用时返回显式的 JSON 状态；池化的运行时并不保证模块全局变量在事件之间存活。把 `previousState` 当作只读 JSON 输入。累加时请构造自己拥有的数组／对象，而不是原地修改宿主支撑的数组。

空闲运行时可以在垃圾回收后存活，池的大小受插件配置的并发数限制。宿主按需创建额外实例并丢弃被中断的实例。取消回调在实例归还池中之前完成，引擎随后丢弃它对已结束调用参数的引用，因此空闲实例不会让上一个请求的数据一直存活；插件保存在模块变量里的值则仍会让它们存活。钩子绑定保持有效；宿主不会冻结导出的函数或对象成员。某个可选钩子（用量钩子、`listArtifacts`、`buildContentRequest`）是否导出，在插件加载时一次性决定：当时为 `undefined` 的导出计为不存在，之后再赋值也不会让宿主调用它。等待下一个上游事件时不占用 JavaScript 执行槽位。

宿主把返回的状态原样传给下一个事件（见[钩子参数与返回值](#钩子参数与返回值)）；钩子对 `previousState` 所做但未返回的改动不会保留。不是纯 JSON 的状态（例如类型化数组）会先通过其 JSON 编码归一化。状态大小仍在每个事件之后按其实际编码字节数检查，包括可能被后续事件替换为更小值的中间状态。

一个完整、以空行分隔、且其钩子返回 `done: true` 的事件会终止读取器并关闭上游响应。最后的状态作为 `response.body` 传给既有的 `parseSubmitResponse`，保留上游 HTTP 状态与请求头。随后走常规的立即完成路径，持久化、结算并呈现结果。SSE 状态是请求局部的；持久的插件状态仍然只有 `parseSubmitResponse` 返回的 `state`。

没有 `done` 就 EOF、帧格式／状态无效、读取失败、钩子失败与超限都会让提交失败 —— 但在原生路由上，一旦有事件已到达客户端则除外（见下文）。事件、累加的 JSON 状态与持久化的任务数据各自限制为 1 MiB；在声明了 `retainResult: false` 的路由上，事件限制为 `MAX_FILE_DOWNLOAD_MB`；数据绝不截断。现有的流式空闲超时（未设置时为 30 秒）、提交上下文期限与逐钩子执行超时同样适用。一旦成功的 SSE HTTP 应答被接受，失败就是不可重试的，包括形如 5xx 的本地错误：重新启动供应商操作可能造成重复的计费工作。选择 `sse` 却拿到 JSON 应答的请求会被当作 JSON 提交读取：早于该扩展发布的网关在其原生路由上就是这样应答的。

在原生路由上，宿主会中继这条流：每个上游事件在插件钩子读取它之前，就以供应商的原始分帧（注释与 keep-alive 行也包括在内）到达客户端，应答为 200 的 `text/event-stream`。因此，向供应商请求流的原生客户端（Seedream 的 `stream: true`、Wan 交错输出的 `X-DashScope-Sse: enable`）收到的是供应商自己的事件；提交呈现器不会被调用，其后也不跟随 JSON，连错误都没有。一旦有一个事件到达客户端，提交即结算且永不退款：

- 当上游正常结束了流（插件报告了 `done`，或上游关闭了它），最后的状态交给 `parseSubmitResponse`，并像任何立即结果一样结算：插件按已交付的内容计费，立即的 `FAILURE` 结算为零。
- 当流以其他方式停止（读取错误、空闲超时或提交期限、钩子失败、状态无效或增量改动无效、大小超限），最后一个有效状态仍会交给 `parseSubmitResponse`（改动无效后为 `null`），但任务按预留额度结算：不调用 `extractUsageOnComplete` 与 `extractUsageOnSubmit`，因此已交付的用量无法降低费用。立即的 `FAILURE` 仍结算为零。客户端的流是被切断而非正常关闭，因此中继它的下游网关也会保留其预留。
- 当 `parseSubmitResponse` 失败或返回无效结果时，任务按预留额度、以网关的任务 id 成功。

因此，首个事件之后的钩子错误会保留预留。插件应把供应商自己的失败事件作为结果上报：`done`，随后 `parseSubmitResponse` 返回立即的 `FAILURE`。

客户端离开并不会取消被中继流的上游请求：宿主会读到末尾并完成结算。keep-alive 注释会重置空闲超时，因此上游请求同样受宿主协议的提交期限约束（`TASK_PLUGIN_PROTOCOL_TIMEOUT_SECONDS`，默认 600 秒）；到达该期限会像读取错误一样终止流。

宿主协议不转发上游事件：Responses 在持久化的提交屏障之后走其既有的呈现流程，并保留其独立设限的提交上下文；图片协议以 JSON 回答。该接口不会在上游完成之前新增任务创建，也不支持流续传。

### 可选的宿主托管 SSE 累加

包含 `sse` 且导出 `parseSubmitEventDelta` 而没有导出 `parseSubmitEvent` 的插件使用 `parseSubmitEventDelta`，声明了 `submit-sse-delta@1` 的插件也一样。描述符仍使用 `responseType: "sse"`。导出 `parseSubmitEvent` 且没有声明 `submit-sse-delta@1` 的插件保留快照钩子与其原有契约，即使它同时导出了 `parseSubmitEventDelta`。

```ts
parseSubmitEventDelta(ctx: DriverContext,
  event: {event: string; id: string; data: string},
  previousState: JSONValue | null
): {changes: JSONChange[]; state: JSONValue; done: boolean}
```

`state` 包含解释下一个事件所需的控制数据，限制为编码后 64 KiB 的 JSON。只有这份快照会被回传给 JavaScript。宿主维护一份独立的结果，初始为 null，并按顺序应用 `changes`：

```js
{op: "set", path: [], value: {text: "", images: []}}
{op: "appendText", path: ["text"], value: "A new text fragment"}
{op: "append", path: ["images"], value: {url: "https://cdn.example/image.png"}}
```

- `set` 在空路径上替换根，替换已存在的数组元素，或新增／替换对象成员。父容器必须已存在。
- `append` 向已存在的数组追加一个 JSON 值。
- `appendText` 向已存在的字符串追加文本。宿主在 Go 侧保留文本，不把累加的文本回传给插件。
- 路径是字符串对象键或非负整数数组索引的数组。索引必须指向已存在的元素；不支持稀疏数组与隐式创建父级。键是数据，绝不是属性访问表达式。

每个结果恰好包含 `changes`、`state` 与布尔值 `done`。每个改动恰好包含 `op`、`path` 与 `value`。每个事件最多 256 个改动，路径最多 32 段，结果根以下最多 32 层、32,768 个结果节点，编码后结果 JSON 最多 1 MiB。大小核算包含转义后的键与字符串、标点与替换，并在每次操作后检查。即使后续操作会让结果变小，超限的中间操作仍会失败。无效操作会让提交无效，或在已中继过事件的原生路由上按预留额度结算；部分结果绝不发布。

宿主统计被改动取值的编码大小，而不是在每个事件上对完整累加结果重新编码。在 `done: true` 时，它实体化常规的 JSON 结果，并在作为 `response.body` 传给 `parseSubmitResponse` 之前，用记录的尺寸核对其实际编码。之后该结果走与快照模式相同的持久化、用量校验与结算路径。状态与构造器都属于单个请求，并在完成、取消或出错时释放；上游 I/O 期间不占用 JS 槽位。

插件仍要解释供应商负载、决定更新哪些字段、区分累计用量与增量，并决定何时完成。阿里把该模式用于交错图片生成，其控制状态只保留内容索引、文本邻接关系与完成原因。
